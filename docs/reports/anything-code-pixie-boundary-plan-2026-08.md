# AnythingWithPixie / CodeWithPixie の住み分け案

作成日: 2026-08-13  
対象: 小型ローカルモデルによる複数コード・複数ドキュメントの調査と編集  
調査時点のブランチ: AWP `feat/pixie-core-facade`、CWP `feat/richcopy-base`

本書の設計対象は AWP と CWP の二者である。兄弟プロジェクトの **TalkWithPixie** は会話コンパニオンであり、コード・文書編集用の `Workset` / `ChangeSet` を必要としないため、`pixie_core` 統合の対象外とする。TalkWithPixie の軽量 ReAct、会話検索、長期記憶は用途に合わせた独立実装として維持する。

## 結論

ユーザー向け機能の方向性は大きく変えなくてよい。ただし、内部仕様には改善余地がある。

- **AnythingWithPixie（以下 AWP）** は、UI に依存しない「調査・計画・編集・検証エンジン」にする。
- **CodeWithPixie（以下 CWP）** は、Monaco を中心とした「人間が確認して操作するワークベンチ」にする。
- CWP の Code / Note / Plan を別エージェントとして育てず、AWP の同じ実行基盤に対する **プロファイル**として扱う。
- 大きなコンテキスト窓は全文投入に使わず、検索結果、依存関係、変更案、検証結果を保持する余裕として使う。
- 複数ファイル編集の共通単位を `Workset` と `ChangeSet` にする。ここが両プロジェクト間の正式な契約になる。

最終的な関係は次の形がよい。

```text
CodeWithPixie
  Monaco / Markdown / Mermaid / ファイルツリー
  選択範囲・未保存バッファ・承認・競合表示
                    │
                    │ WorkspaceSnapshot / Workset / ChangeSet / Events
                    ▼
AnythingWithPixie / pixie_core
  調査ループ・索引・依存解析・計画・編集案・検証・Web調査
                    │
                    ▼
  Qwen / Gemma / LFM、ファイルシステム、テスト、検索サービス
```

## 実装状況（2026-08-14）

本設計の第1縦断スライスを3プロジェクトへ実装した。

- AWP: `pixie_core` API 1.7 と `Engine.set_workspace_snapshot()` を追加した。`read_file`、`write_file`、`append_to_file`、`replace_lines`、`search_and_replace` はセッション別の未保存バッファを優先し、部分編集後も同じバッファを更新する。
- CWP: Code モードも `current_content` を送り、各ターンで AWP の WorkspaceSnapshot を更新する。承認diffもディスク版ではなく同じ未保存バッファを基準に計算する。
- TalkWithPixie: 検索前のLLMプランナーを廃止した。通常会話は常駐メインモデルへ直行し、明示的な単発検索はPythonルール、実装箇所・原因・依存関係などの複雑なローカル調査だけ既存ReActへ送る。ルーティング専用のCPU/GPUモデルは使用しない。
- TalkWithPixie: `phone-launch.log` を `.gitignore` へ追加した。既存ログに実トークンが含まれる場合の失効・再発行は運用作業として別途必要である。

現在は `WorkspaceSnapshot`、AST/Markdown索引付き `Workset`、`pixie_core` API 1.10 のjournal付き `ChangeSet` まで実装済みである。CWP の現在ファイルとピン留めファイルは未保存内容を snapshot に保持し、モデルへは必要な構造だけを渡す。ChangeSetはbase hash競合、一括preview/承認、原子的置換、作成・変更・削除を含むrevertを提供する。Markdownは節・frontmatter操作と、要件ID・用語定義・リンク・Mermaid整合性を検査する。本文は必要時に `read_file` で取得するため、チェック済みファイル全文を毎ターン prefill しない。文書間の権威順を含む本格文書グラフとWeb EvidenceSetは未実装である。

## 今回の調査方法

小型モデルでの運用を想定し、リポジトリ全体を一括投入せず、次の境界だけを静的に追った。

- `pixie_core` の公開 API とツール選択
- CWP の `engine_adapter.py`
- Code / Note / Plan のルーティング
- 選択範囲、未保存バッファ、参考ファイルの注入
- 書き込み前プレビュー、承認、競合検知、ロールバック
- 会話圧縮と履歴同期
- 関連する重点テスト

CWP の重点テストは **76 passed**。今回の提案は既存機能の不具合修正だけを目的とせず、今後の性能と保守性を上げるための境界整理である。ただし調査中に、Code モードでは未保存バッファ全文がエージェントへ渡らないという仕様・実装上の不整合も確認した。

## 現在の構成

### AWP がすでに持っているもの

AWP の実体は `src/pixie_core` にあり、CWP から利用できる埋め込み API が用意されている。

- `create_engine()` とセッション単位の `Engine`
- ReAct 実行ループとツール呼び出し
- 読み取り・書き込み・コマンド系ツール
- `fixed_tool_set` による固定ツールプロファイル
- `active_packs` による任意ツールパック
- 会話履歴の取得、削除、置換
- コード索引、サブエージェント、状態ボード
- CLI と CWP の双方から利用できる公開境界

これは「エージェントの頭脳」を AWP に集約できる土台として十分である。

### CWP が持っているもの

CWP はすでに高機能な編集ワークベンチである。

- Monaco エディタ、未保存バッファ、選択範囲
- ファイルツリー、全文検索、一括置換
- Markdown プレビュー、Mermaid / mdflow 編集
- Confluence とのリッチコピー・取り込み
- Code / Note / Plan モード
- SSE ストリーミング、停止、承認 UI
- 書き込み前の差分表示と「修正して承認」
- mtime による外部変更との競合検知
- UI 保存履歴と、エージェントターンのロールバック
- ワークスペース・モデル・コンテキスト長の設定

したがって CWP を別の推論エンジンにする必要はない。強みは、人間とエージェントの共同編集に必要な表示・操作・安全確認にある。

## 現在の重複と性能上の問題

### 1. 参考ファイルを文字数で詰め込んでいる

CWP は現在、チェックされたファイルを **1ファイル最大8,000文字**、**1ターンの参考ファイル総量最大60,000文字**として、順番にメッセージへ埋め込む。選択範囲には別枠で最大8,000文字の制限がある。これらは参考ファイルや選択範囲が指定されたターンにだけ加わるもので、無条件に毎ターン60,000文字を投入するわけではない。明示選択を優先できる点はよいが、複数コード・複数文書では次の問題が出る。

- 重要度ではなくチェック順・ファイル順に予算が消費される。
- ファイル先頭だけが残り、必要な関数や節が後半にあると欠落する。
- 同じ内容が会話履歴に再投入され、長いコンテキストでも KV キャッシュを浪費する。
- 128K 以上の窓でも、関係の薄い本文が推論精度を下げる。
- 変更後に古い抜粋が履歴へ残り、現在のファイルと矛盾する。

さらに Code モードでは、フロントエンドが `current_file` と選択範囲を送る一方、`current_content`、つまり現在開いているファイルの未保存全文を送っていない。サーバ側も Code 用メッセージにはパスだけを載せる。そのため現在は次の非対称がある。

- Note / Plan: 現在ファイルの未保存バッファを最大8,000文字まで利用する。
- Code: 選択範囲は未保存内容を利用できるが、それ以外はエージェントがディスク上の版を読む。

Code モードで「現在ファイルは未保存編集込みの方を優先する」というコメントやテスト名があるものの、全文は実際には渡っていない。これは `WorkspaceSnapshot` と仮想バッファ読み取りを最優先に導入すべき直接的な理由である。

この処理は GUI ではなく AWP のコンテキスト選択器が担当すべきである。CWP は「ユーザーが明示的に選んだ」という強い優先度だけを渡す。

### 2. 編集の意味論が二重実装になっている

CWP は承認画面用に `write_file`、`search_and_replace`、`replace_lines` の結果を再計算している。また Note モードには別の `search/replace` ブロック適用器がある。

これらは AWP の実ツールと将来ずれる可能性がある。たとえばファジーマッチ、改行、エンコーディング、複数一致、行範囲の扱いが片側だけ変更されると、承認画面で見た結果と実行結果が一致しなくなる。

必要なのは CWP に編集ロジックをコピーすることではなく、AWP が同じ意味論で **プレビュー可能な構造化変更**を返すことである。

### 3. Code / Note / Plan のオーケストレーションが CWP に寄っている

CWP は `AgentSession`、`NoteSession`、`PlanSession` を持ち、ツール集合、システム指示、履歴、承認方法を切り替えている。現状は正常に動くが、次の機能を足すたびにモード間差分が増える。

- Workset の自動構築
- 文書間の整合性検査
- 複数ファイル変更のトランザクション管理
- 変更後のテストと再計画
- Web 根拠の保存
- モデルの段階的エスカレーション

モードは AWP 側の `AgentProfile` とし、CWP はプロファイル名と UI 入力を渡すだけにする方がよい。

### 4. ロールバックがワークスペース全体の部分スナップショットである

CWP のエージェント用ロールバックは、各ターン前にテキストファイルをメモリへ保存する。ただし **1ファイルが1 MBを超える場合はファイル全体が対象外**となり、スナップショットの総量が30 MBに達すると以降のファイルは保存されない。新規作成ファイルも削除しない。

安全策としては有用だが、プロジェクトが大きくなるほど走査コストが増え、「一部だけ戻った」状態を作り得る。エージェントが実際に触る予定のファイルを `ChangeSet` に列挙し、その before hash と before content を記録すれば、走査不要で完全性も判定できる。

### 5. コンテキスト長をバックエンドの private 属性へ反映している

CWP は取得できないコンテキスト長を `engine.context.llm._n_ctx` に上書きしている。実用上の回避策だが、モデル能力、サーバ設定、実際に確保された KV キャッシュが一致する保証はない。

AWP の公開 API に `ContextCapabilities` を設け、次を区別すべきである。

- モデルが対応すると宣言する最大長
- サーバが起動時に確保した長さ
- セッションで使用してよい上限
- 入力、出力、ツール結果、要約に割り当てる予算

## 推奨する責務分担

| 機能 | AWP / pixie_core | CWP |
|---|---|---|
| モデル接続・function calling | 所有 | 設定 UI |
| ReAct ループ・再計画 | 所有 | 進捗表示・停止操作 |
| コード・文書の索引 | 所有 | 手動更新・状態表示 |
| Workset 選定 | 自動選定・順位付け | ピン留め、選択範囲、未保存バッファ提供 |
| Code / Note / Plan | プロファイルとして所有 | モード選択 UI |
| 変更案の生成 | `ChangeSet` として所有 | diff 表示、ユーザー修正 |
| 編集適用の意味論 | 所有 | 承認・却下操作 |
| 複数ファイルのトランザクション管理 | 所有 | 結果と競合の表示 |
| テスト・lint・文書整合性検査 | 所有 | 実行状況と結果表示 |
| Web 検索・出典・証拠 | 所有 | 出典ビュー、採用・除外操作 |
| Monaco・Markdown・Mermaid | 依存しない | 所有 |
| UI 手動保存の履歴 | 関与しない | 所有 |
| 外部変更の mtime 競合 | hash 契約を提供 | 検出・ユーザー判断 |
| エージェント変更の rollback | ChangeSet 単位で所有 | 操作 UI |
| SSE / HTTP | イベント型を定義 | 配信アダプタを所有 |

重要なのは、「適用ボタンは CWP、何がどう適用されるかという規則は AWP」という分担である。

## 共通 API の提案

### `WorkspaceSnapshot`

CWP が現在の編集状態を AWP に渡すための入力。

```json
{
  "workspace": "D:/repo",
  "revision": "optional-git-or-snapshot-id",
  "buffers": [
    {
      "path": "src/auth.py",
      "content": "未保存の最新内容",
      "base_hash": "sha256-of-disk-version",
      "dirty": true,
      "selection": {"start": 120, "end": 360}
    }
  ],
  "pinned_paths": ["docs/auth.md"]
}
```

AWP の読み取りツールは、同じパスならディスクより未保存バッファを優先する。これにより、巨大な本文をユーザーメッセージへ毎回貼らずに済む。

### `Workset`

1 件の依頼に必要な断片だけを集めた作業集合。

```json
{
  "task": "認証方式の変更",
  "items": [
    {"path": "src/auth.py", "ranges": [[40, 130]], "role": "target", "score": 1.0},
    {"path": "src/routes.py", "symbols": ["login"], "role": "caller", "score": 0.84},
    {"path": "tests/test_auth.py", "symbols": ["test_login"], "role": "test", "score": 0.79},
    {"path": "docs/auth.md", "sections": ["ログイン"], "role": "spec", "score": 0.73}
  ],
  "omitted": [{"path": "...", "reason": "low_score"}]
}
```

構築順は、ピン留め・選択範囲、シンボル検索、参照先・呼出元、テスト、関連文書、必要時だけ全文、がよい。

### `ChangeSet`

複数ファイルをまとめて確認・適用・検証・巻き戻しする単位。

```json
{
  "id": "chg_...",
  "changes": [
    {
      "path": "src/auth.py",
      "base_hash": "...",
      "operations": [{"kind": "replace_range", "start": 120, "end": 240, "text": "..."}]
    },
    {
      "path": "docs/auth.md",
      "base_hash": "...",
      "operations": [{"kind": "replace_section", "heading": "ログイン", "text": "..."}]
    }
  ],
  "verification": ["python -m pytest tests/test_auth.py"]
}
```

AWP は次の段階を提供する。

1. `preview_changeset` — 全ファイルの適用後内容と競合を計算
2. `validate_changeset` — hash、重複編集、パス、安全条件を確認
3. `apply_changeset` — 検証済み内容をステージし、変更記録を残して反映
4. `verify_changeset` — 対象テスト・lint・文書リンク等を実行
5. `revert_changeset` — 作成ファイルを含めて元に戻す

CWP はその結果をタブ付き diff で表示し、ユーザーが一部を編集した場合は変更済み `ChangeSet` を再検証してから適用する。

一般的なファイルシステムでは、複数ファイルを一度に置換する厳密な原子性は保証できない。実装では全対象の `base_hash` を先に検証し、同一ファイルシステム上の一時ファイルへ書き出し、変更ジャーナルを永続化してから順次置換する。途中失敗時は journal から復元し、プロセス異常終了後も次回起動時に「完了・rollback・手動解決」を選べる状態にする。`base_hash` は文字列ではなく元ファイルのバイト列から計算し、エンコーディングと改行形式も ChangeSet に保持する。

### `AgentProfile`

```text
code: 調査 + ChangeSet 作成 + 検証。書き込みは承認制
note: 文書グラフ調査 + ChangeSet 作成。既定では自動適用しない
plan: 読み取り + Workset + 実行計画のみ
research: ローカル/Web調査 + EvidenceSet。書き込み不可
```

プロファイルはツール集合だけでなく、許可する副作用、コンテキスト予算、終了条件、検証方針を含める。CWP 固有の Mermaid や Copilot ツールは tool pack として登録できるが、実行ループは共通にする。

## 小型モデル向けの実行方法

### 1. 1 回で全部やらせない

複数ファイル編集は次の短いフェーズに分ける。

```text
依頼の構造化
  → 候補検索
  → Workset 確定
  → 変更計画
  → ChangeSet 生成
  → 静的検証
  → 人間の承認
  → 適用
  → 対象テスト
```

各フェーズの出力を JSON で固定すると、8B 前後でも長い自由文を維持する必要がなくなる。

### 2. 長いコンテキストを三層に分ける

- **常駐層**: システム指示、ツール schema、タスク、変更禁止事項
- **作業層**: 現在の Workset、関連シンボル・節、未保存バッファ
- **証拠層**: 必要時に再取得する全文、テストログ、Web ページ

履歴の古いツール出力は常駐させず、`DecisionLog` と `ArtifactRef` に畳む。128K の窓があっても通常ターンは 16K–32K 程度に抑え、難しい統合時だけ 64K–128K を使う。

### 3. モデルを役割分担する

既存のモデル候補を使うなら、次の構成が扱いやすい。

- **LFM 系の小型モデル**: 依頼分類、検索クエリ生成、候補の順位付け、要約
- **Gemma 4 系**: 文書横断の整合性、長い仕様の統合、通常の編集計画
- **Qwen 3.6 系**: 複数コード編集、ツール利用、難しい変更の最終 ChangeSet

ただしモデル名を各モードへ固定しない。まず最小モデルで Workset を作り、次の場合だけ上位モデルへ送る。

- 変更対象が 5 ファイル以上
- 公開 API、DB schema、認証、並行処理に影響
- Workset の候補が収束しない
- テスト失敗後の再計画
- コードと複数仕様書を同時に整合させる

モデル選定と最新情報の詳細は [small-model-web-performance-plan-2026-08.md](small-model-web-performance-plan-2026-08.md) を参照。

## コード編集と文書編集の住み分け

### コード編集

AWP が所有するもの:

- シンボル、import、呼出元、設定、テストの関係グラフ
- 変更影響範囲と Workset
- 構文を意識した ChangeSet
- 対象テスト選択、lint、型検査、失敗時の再計画

CWP が所有するもの:

- 選択中コードと未保存バッファ
- 複数ファイル diff
- 承認前の手修正
- 外部エディタ変更との競合 UI
- テストログへのジャンプ

### 文書編集

AWP が所有するもの:

- 見出し単位の文書索引
- 用語、要件 ID、リンク、コードシンボル、図 ID の関係
- 「根拠文書」「派生文書」「参考資料」の権威順
- 複数文書の整合性マトリクス
- 節単位の ChangeSet とリンク・Mermaid 参照検査

CWP が所有するもの:

- Markdown 編集とプレビュー
- 選択中の節
- Mermaid / mdflow の直接操作
- Confluence 入出力
- 変更箇所の視覚的確認

文書もコードと同じ ChangeSet を使う。ただし操作種別に `replace_section`、`insert_after_heading`、`update_frontmatter` などを追加すると、小型モデルが長い全文を再生成せずに済む。

## Web 調査の配置

Web 調査は最終的に AWP の `research` プロファイルまたは tool pack に置く。CWP 固有のブラウザ連携を残す場合も、結果は共通の `EvidenceSet` に変換する。

ただし調査時点では、AWP に `src/toolpacks/web.py` は存在しない。`src/mcp_client.py` は試作コードとテストから参照される段階で、`pixie_core` の実行経路には接続されていない。CWP の `web2md` も PrayLight の外部プロセスに依存している。したがって `research` プロファイルは、Webプロバイダー抽象化、取得制限、引用・出典保存、失敗時のフォールバックを先に実装してから導入する。

```json
{
  "query": "...",
  "claims": [
    {
      "claim": "...",
      "sources": [{"url": "...", "title": "...", "retrieved_at": "..."}],
      "confidence": 0.82
    }
  ]
}
```

これにより、検索ログ全文を毎ターン持たず、採用した主張と出典だけをコード・文書編集へ渡せる。CWP は出典をクリック可能にし、ユーザーが採用・除外できるようにする。

## 仕様として改善すべき点

ユーザー向けの主要機能は維持してよいが、次を正式仕様に追加すべきである。

1. 未保存バッファは常にディスク内容より優先する。
2. 明示選択・ピン留めは自動検索より優先するが、全文常駐を意味しない。
3. 変更は必ず ChangeSet と base hash を持つ。
4. 複数ファイル変更は全件検証・ステージ後に、復旧可能な journal 付きトランザクションとして適用する。
5. プレビューと実適用は同じ編集関数を使う。
6. 新規作成・変更・削除をすべて巻き戻せる。
7. Code / Note / Plan で履歴・コンテキスト・ツール制限の契約を共通化する。
8. Web 由来の内容は取得日時・URL・採否を保持する。
9. コンテキスト超過時は黙って先頭切り詰めせず、何を省略したか構造化して返す。
10. 検証失敗時は適用済み状態、未適用状態、ロールバック可否を明示する。

## 移行順序

### Phase 0: 公開基盤を確定する

- 調査時点で未マージの AWP `feat/pixie-core-facade` をレビューし、master 系へ統合する。
- CWP が参照する `pixie_core` の配布・配置方法を確定する。現在の `sys.path` 注入を当面維持する場合も、対応ブランチに偶然依存しない状態にする。
- CWP に既にある起動時の `API_VERSION` 検査と明確なエラー表示を維持し、Phase 1 が要求する公開 API バージョンへ更新する。
- AWP が存在しない環境でスキップされる2つのテストモジュールについて、CIでは AWP/CWP 統合テストとして必ず実行する構成を追加する。

Phase 1 以降は `pixie_core` の公開境界が master 系で利用できることを着手条件とする。

### Phase 1: 境界だけ整える

- AWP に `WorkspaceSnapshot` と仮想バッファ読み取りを追加する。
- AWP に編集プレビュー API を追加し、CWP の `_tool_preview` と `patch.py` をそこへ委譲する。
- private な `_n_ctx` 上書きを公開 `ContextPolicy` API へ移す。

既存 UI とプロンプトをほぼ変えず、最も危険な二重実装を先に減らせる。

### Phase 2: Workset を導入する

- CWP のチェック項目を `pinned_paths` として渡す。**最小実装済み**。
- AWP が関連テスト・文書候補を追加する。**ファイル名・配置による低コスト候補は実装済み**。シンボル、呼出元、文書節を使う索引連携は未実装。
- 生の全文貼り付けをやめ、必要断片をターンごとに取得する。**Code モードで実装済み**。
- Workset と省略理由を CWP で確認できるようにする。

ここが小型モデルの速度・精度に最も効く。

### Phase 3: ChangeSet を導入する

- 書き込みツールを直接実行せず、まず ChangeSet を生成する。
- CWP の承認画面を複数ファイル ChangeSet 対応にする。
- base hash 競合、journal 付き適用、作成ファイルを含む rollback を AWP に集約する。
- 検証結果を ChangeSet にひも付ける。

### Phase 4: モードをプロファイルへ統合する

- NoteSession / PlanSession 固有の実行ロジックを `AgentProfile` へ移す。
- CWP は profile、snapshot、user request を渡し、共通イベントを表示する。
- 文書グラフを追加する。EvidenceSet は Web プロバイダーと `research` プロファイルの実装完了後に追加する。
- 小型ルーターから必要時だけ上位モデルへエスカレーションする。

## 当面維持してよいもの

- CWP の Monaco、Markdown、Mermaid、Confluence 機能
- 人間による承認を必須にする現在の安全思想
- Code モードで自動保存しない方針
- CWP の UI 操作に対するディスク永続のローカル履歴
- AWP の `pixie_core` 公開パッケージ境界
- CWP 固有機能を tool pack で追加する仕組み

## 最優先の実装項目

最初に実装するなら **WorkspaceSnapshot + Workset** がよい。理由は、複数ファイル編集の性能問題の中心がモデルサイズではなく、「何を、どの版で、どれだけ読ませるか」だからである。

その次に ChangeSet を入れる。これで Code と Note の編集経路、差分プレビュー、承認、検証、rollback を共通化でき、AWP と CWP の住み分けが完成する。

## 検証時に確認した周辺課題

以下は本設計の主題ではないが、着手前後に別チケットで管理すべき事項である。

- TalkWithPixie の未追跡 `phone-launch.log` は `.gitignore` 対象外で、URLと認証情報らしい文字列を含む。ログを無視対象へ追加し、値が実際の認証トークンなら失効・再発行する。ログの削除だけでは漏えい済みトークンへの対処にならない。
- AWP は調査時点で `pixie_core.tool_count()` が **35**。README の35ツール表記と一致する。
- AWP のテストには Windows の日本語コンソール復号、ruff 検出、`.venv` 探索に関係する環境依存失敗が5件あり、アーキテクチャ移行とは分けて修正する。
- CWP の `static/js/app.js` は調査時点で **4,378行**。単一ファイルとして大きいため、Workset / ChangeSet UI を追加する前に、状態管理、チャット、差分、設定などの境界で段階的に分割する。
- CWP の `run_command` は承認ゲートを持つが、承認後の任意シェル実行を許す。ChangeSet の安全性とは別に、許可コマンド、作業ディレクトリ、環境変数、タイムアウト、監査ログのポリシーを定義する。
