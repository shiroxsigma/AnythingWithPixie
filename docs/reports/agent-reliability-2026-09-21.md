# エージェント実行の信頼性改善（2026-09-21）

実務での失敗に直結する「途中完了」「不十分な検証の受理」「通信異常の成功扱い」を改善した。
モデルそのものの能力や、あらゆる開発課題での成功を保証する変更ではない。

## 修正内容

- 編集直後にテストが通っても、次の推論からツールを取り上げない。後続の文書更新や追加修正を続けられる。
  実際の検証済み完了報告は従来どおり短い応答でも受理する。
- `pytest test_app.py -k smoke`、`-ksmoke`、`-mfast`、`--deselect` などで
  対象を絞った実行は、Workset全体の検証完了を裏付ける証跡にしない。
- 接続待ち・再試行・本文受信中のタイムアウト、切断、不正な応答を終端エラーに統一。
  部分出力を受け取った後は生成を自動再送しない。キャンセルと上限到達はそのまま伝播する。
- 補助エージェントもエラーを検出し、途中の生成やツール呼び出しを成功として利用しない。
  要約生成に失敗しても既存のホワイトボードを上書きしない。
- evalの標準出力チェッカーは、出力一致に加えて終了コード0を要求する。
- Bonsai 2の無応答待機を既定120秒にし、起動・接続先切り替え・委譲先・埋め込みAPIで
  同じ接続設定を適用する。全体上限は既定180秒。無限大・NaN・非正数は拒否する。
- Bonsai 2のツール結果は `role="tool"` と元の `tool_call_id` を保って送信する。
  CLI・接続先切り替え・埋め込みAPI・evalで同じ判定を使い、LFM専用の `tool_choice` 処理とは分離する。
  調査・レビューを別モデルへ委譲する場合は、選択した委譲先の対応状況で判定する。
- Bonsai 2の推論強度は `medium` を既定にし、接続設定やリクエストで上書き可能にする。
  [公式モデルカード](https://huggingface.co/prism-ml/Ternary-Bonsai-2-27B-gguf#best-practices)は
  サーバー既定の `xhigh` に対し、`medium` を短い応答向けとして案内している。
  [PrismMLのAPI](https://github.com/PrismML-Eng/llama.cpp/blob/prism/tools/server/README.md#post-v1chatcompletions-openai-compatible-chat-completions-api)に従い、トップレベルの `reasoning_effort` を送信する。

システムプロンプトを固定し、動的情報を末尾にのみ付与する既存のキャッシュ設計は維持した。
ローカルの `config.json` に `http://127.0.0.1:8098/v1` / `bonsai2-27b` の選択肢も追加した。

## 検証

変更前のpytestは604成功、1スキップ。追加した設定テストが作業ディレクトリの束縛を
後続テストへ漏らして7件失敗する問題を検出し、テストを独立したContextで実行するよう修正した。
関連40件の連続実行で解消を確認した。
推論強度の送信・上書き設定とBonsaiのツール結果形式まで含む全体pytestは742成功、1スキップ。
その後、最終レビューで見つけた混成サーバー間の委譲を修正し、追加15件を含む関連80件が成功した。
最終テスト定義は758件（成功を確認した757件と、POSIXパス限定の1スキップ）。
追補の対象は `test_subagent_tool_roles.py`、`test_delegate_research.py`、
`test_subquery_completion_errors.py`、`test_bonsai_tool_role.py`。
変更対象のlintと `git diff --check` は成功。全体lintには、今回未変更のファイルに
既存指摘が残るため、リポジトリ全体のlint成功は主張しない。

追加eval `12_post_test_documentation` は、実装修正→unittest→README更新を要求する。
実装だけ直してテストが成功しても、READMEが古ければ失敗する。元のテストを弱めても
ハッシュ検証で失敗する。完成したfixtureでは全8チェック成功。
実行順序はプロンプトで要求し、最終状態のチェッカー自体では時系列まで証明しない。

実モデルの検証先は `http://127.0.0.1:8098/v1`、モデルは `bonsai2-27b`（PQ2_0）、
コンテキスト32,768。通常のevalワーカーへTurnControlを束縛し、ターン360秒、
ストリーム180秒、無応答120秒で実行した。旧evalランナーのタイムアウトは
ワーカー終了待ちがあるため、そのままでは厳密な時間上限を保証しない。

| ケース | 結果 | 証拠 |
|---|---|---|
| 存在しない設定ファイルを調べて報告 | 成功、71.18秒、4ツール | `evals/results/eval_20260921_080347.json` |
| 実装・検証・文書更新（推論強度未指定） | 360秒上限、未完了 | `evals/results/eval_20260921_081033.json` |
| 実装・検証・文書更新（medium、ツール結果形式修正前） | 実装修正と4テスト成功。README更新前に360秒上限 | `evals/results/eval_20260921_081728.json` |
| 実装・検証・文書更新（medium、ツール結果形式修正後） | 実装修正と4テスト成功。README更新前に360.03秒上限 | `evals/results/eval_20260921_082654.json` |

`evals/results/` の生レポートはローカル生成物でGit管理対象外。
推論強度未指定での失敗は、`medium` 追加前の観測値として残す。
タイムアウト時の既存ランナーは途中の集計を失うため、レポート中の `tools=0` は実呼び出し数を示さない。
2回目の試行はtrajectory上で8ツール実行、実装変更、unittest成功を確認した。
3回目もREADME更新は完了していないため、合格とは扱わない。ツール結果の参照IDは整合し、
システム文面とツール定義も実行中に変化していなかった。`medium` は時間上限ではなく、
この試行では一度の生成に1,719トークン・約103秒かかる場面があった。
trajectory上では10ツールが成功。生成時間以外にも計測上の待ち時間があるが、
既存ログはリクエスト開始・初回チャンク到着を記録していないため、その原因は未特定。
残った作業ディレクトリへ8チェックを再適用すると4件成功。unittest、README見出し、API表記、
依存関係の説明は合格した。時間制限、新しい動作説明、検証コマンド、旧説明の除去は未達。
元のテストファイルのハッシュは一致しており、テスト改変による成功ではない。
trajectoryではunittest成功後にREADME更新予定を記録していたが、実際の編集は行われていなかった。

## 残る測定上の制約

今回の少数の実機試行から一般的な成功率や速度改善率は算出できない。
比較eval全体については、ワーカーのキャンセルと、エージェントが変更できるテストを
採点根拠としているケースの整備が残る。新設taskでは元のテストの不変性を検証している。
